## 1️⃣ 数量翻倍（4 个常量 + 1 个兜底上限）

| 常量 | 文件:行 | 改前 | 改后 | 说明 |
|---|---|---|---|---|
| `ARC_MAX` | ShockArcs.java:152 | 44 | **88** | 单实体弧数上限 |
| `APPARENT_GAIN` | ShockArcs.java:165 | 160 | **320** | 目标条数 = GAIN × 半径 / 距离 |
| `SPAWN_PER_TICK` | ShockArcs.java:173 | 7 | **14** | 补生速率（7×20×0.325s≈45 条 < 44 上限已经配平；只翻 ARC_MAX 而不翻它 ⇒ 上限永远补不满 = 假翻倍） |
| `ARC_TOTAL_MAX` | ShockArcs.java:185 | 140 | **280** | 全场总预算（多目标按比例缩水） |
| `FRAME_VERT_MAX` | ShockArcs.java:209 | 20000 | **36400** | 全场每帧顶点硬上限 = 最坏 29120 × 1.25 |

### ⚠ 为什么 `FRAME_VERT_MAX` 必须跟着改（否则"翻倍"是假的）
最坏单弧 = 主干 `12×SEGMENTS(6)`=72 + 细丝 `FILAMENT_MAX(2)×16`=32 = **104**；
全场最坏 = 280 × 104 = **29120 > 20000** ⇒ 不改的话最坏情况会被这道保险**静默截断**（后半场的弧整批不画）。
36400 = 29120 × 1.25，让最坏情况重新落回护栏以内。**"超限 ⇒ 截断 + 限流 warn"的行为原样保留**，
只是 warn 文案里的数字改成从 `ARC_TOTAL_MAX` 现算（不再写死 140/14560）。

### 为什么 36400 这个数本身也安全（实测取证，不是估的）
- 顶点格式 `DefaultVertexFormat.POSITION_TEX_COLOR` = **24 字节/顶点** ⇒ 29120 顶点 = **682.5 KB**，顶到上限 36400 = **853 KB**；
- 1.20.1 的 `Tesselator` 是 `new BufferBuilder(2097152)`，`BufferBuilder` 构造里 `capacity = 入参 × 6`
  = **12.58 MB**，并且每写完一个顶点都会检查"装不下就按 2 MB 取整扩容"（只打一条 DEBUG 日志）
  ⇒ 即使真顶到上限也只用到 **6.8% 容量**，既不越界也不会触发扩容。
  （取证来源：ForgeGradle userdev 解出的 `com/mojang/blaze3d/vertex/Tesselator.java`、`BufferBuilder.java`。）

## 2️⃣ 颜色：恢复"明蓝 + 白蓝"两档（含"芯白 / 晕蓝"分层）

| 常量 | 文件:行 | 值 | 说明 |
|---|---|---|---|
| `COLOR_BLUE_R_MIN/MAX` | ShockArcs.java:276 | 0.25 ~ 0.40 | **明蓝档**芯色 r |
| `COLOR_BLUE_G_MIN/MAX` | ShockArcs.java:277 | 0.55 ~ 0.70 | 明蓝档芯色 g |
| `COLOR_BLUE_B` | ShockArcs.java:278 | 1.00 | 明蓝档芯色 b |
| `COLOR_WB_R_MIN/MAX` | ShockArcs.java:280 | 0.75 ~ 0.90 | **白蓝档**芯色 r |
| `COLOR_WB_G_MIN/MAX` | ShockArcs.java:281 | 0.88 ~ 0.96 | 白蓝档芯色 g |
| `COLOR_WB_B` | ShockArcs.java:282 | 1.00 | 白蓝档芯色 b |
| `BLUE_FRAC` | ShockArcs.java:288 | **0.40** | 明蓝档比例（每 5 条里 2 条明蓝、3 条白蓝） |
| `HALO_BLUE_R/G/B` | ShockArcs.java:296 | 0.10 / 0.32 / 1.00 | 明蓝档**外辉光带（光晕）**色 |
| `HALO_WB_R/G/B` | ShockArcs.java:297 | 0.34 / 0.56 / 1.00 | 白蓝档**外辉光带（光晕）**色 |

- 改前的写法（已删除）：`temp = 0.55 + 0.45×rnd` 后在 `ShockEffects.EDGE(0.40/0.60/1.0)`
  与 `CORE(0.82/0.96/1.0)` 之间插值 ⇒ **所有弧都落在偏白的 0.55~1.0 区间**，
  这正是"只有白蓝、没有明蓝"的原因。
- `ShockEffects.CORE_*/EDGE_*` 常量保留（注释已改成"历史色档 + 兼容用"），围弧不再引用它们。

### 概率的实现方式（逐弧独立掷骰，不是按顺序分配）
`spawn()`（ShockArcs.java:507）里掷**两枚互不相关的骰子**：
```java
a.longArc = rnd.nextFloat() < SEG_LONG_FRAC;   // 长度档：33.3% 长
float segLen = sampleSegLen(rnd, a.longArc);
sampleColor(a, rnd);                            // 颜色档：40% 明蓝
```
`sampleColor()`（ShockArcs.java:562）内部 `rnd.nextFloat() < BLUE_FRAC`，档内再在区间里均匀取值
（同一档里也没有两条颜色完全一样的弧）。⇒ "长"与"明蓝"是**独立**的两枚骰子，四种组合都会出现。

### 为什么选"两档 + 芯/晕分层"而不是只做两档
片元着色器 `rendertype_lightning_arc.fsh` 会把**每条带子的中轴往白里混**
（`col = mix(vColor.rgb, vec3(1.0), white*0.9)`，`white = smoothstep(0.35, 0.0, |v|)`）——
也就是"带子的正中间一定是白的"，**只有两侧翼保留 `vColor.rgb`**；
而外辉光带比主干宽 3 倍，弧外面那一圈光（中远距离上真正被看见的部分）就是它。
所以：**要让"蓝"被看见，能调的只有"两侧翼 + 光晕带"的颜色** ⇒
`ArcGeometry` 新增了一个重载（`ArcGeometry.java:286`），让外辉光带**单独收一组颜色**；
旧重载（`ArcGeometry.java:259`）保留原来的"芯色 × 0.45/0.55"派发，其它调用点观感不变。
⚠ `vColor.a` 不参与着色器（亮度/生灭必须落在 **RGB 与线宽** 上）—— 这条约定原样保持，
新加的光晕色也同样乘 `lum`。

## 3️⃣ 长度：1/3 长、2/3 短

| 常量 | 文件:行 | 改前 | 改后 |
|---|---|---|---|
| `SEG_MIN` | ShockArcs.java:226 | 0.14 | **0.10**（硬下限，夹取用） |
| `SEG_MAX` | ShockArcs.java:228 | 0.60 | **0.95**（硬上限，夹取用） |
| `SEG_SHORT_MIN/MAX` | ShockArcs.java:233/235 | —（新增） | **0.10 ~ 0.28**（短档，贴身小跳弧） |
| `SEG_SHORT_FRAC` | ShockArcs.java:237 | —（新增） | **0.6667**（2/3） |
| `SEG_LONG_MIN/MAX` | ShockArcs.java:246/248 | —（新增） | **0.45 ~ 0.95**（长档，窜出去的粗长弧） |
| `SEG_LONG_FRAC` | ShockArcs.java:256 | —（新增） | **1/3 = 0.33333** |
| `SEG_LONG_WIDTH_GAIN` | ShockArcs.java:262 | —（新增） | **1.25**（长档线宽 ×1.25 ⇒ 用户说的"粗长弧"） |

- 上一版是 `SEG_MIN~SEG_MAX = 0.14~0.60` 的**均匀分布** ⇒ 长度只是均值附近的噪声，
  肉眼读成"所有弧一样长"（用户这次的反馈）。两档之间**刻意留 0.28~0.45 的空档**，分布不连续才看得出层次。
- **概率实现**：`sampleSegLen(rnd, longArc)`（ShockArcs.java:548），档位由上面那枚
  `rnd.nextFloat() < 1f/3f` 决定 ⇒ 逐弧独立随机，实测 33.3% / 66.7%。
- **长度怎么落地**：`clampLength(...)`（ShockArcs.java:682）**仍然只改第二个端点的偏移**
  （`a.ob* = p0 + û·segLen − anchor_b`），所以"夹取后仍跟随模型"这条不变；
  无论"往回收"还是"往外推"，最终长度都**恰好**等于抽到的 `segLen`（离线 200 万样本最大偏差 2.4e-7）。

### "长而不穿身"怎么保证
1. **最近邻策略保留**（`NEIGHBOR_TRIES = 6`，ShockArcs.java:622）：第二个锚点仍是 7 次随机试探里
   **离第一个最近**的那个 ⇒ 方向天然是"体表局部"的，不会出现随机的手到脚配对；
2. **长档专属的径向镜面**（`clampLength` 内 `if (segLen > SEG_SHORT_MAX)`）：把方向里
   **指向体内**的径向分量翻成向外（`û' = û − 2(û·r̂)r̂`，切向分量与模长都不变）
   ⇒ 长档端点不会比起点更靠内；离线 200 万样本：**端点落进身体体积的比例 旧 2.92% → 新 0.07%**（长档）；
3. **本体深度值兜底**：本 pass 只关深度**写**、没关深度测试，任何仍然贴进身体的部分会被本体遮掉
   ⇒ 绝不会出现"一道亮线从手穿到脚"糊在屏幕上。
   （短档**刻意不做**第 2 条修正：最长 0.28 格够不着身体另一侧，改了只是白白改动已确认的观感。）

## 5️⃣ 用户验证步骤（**不要**由我启动客户端）

1. **数量约翻倍**：对同一个目标（监守者最明显）触发感电，近距第三人称看 —— 弧的**密度**应明显高于上一版。
   客观口径：`/yiz fxtoggle status` 看 `弧=`；日志 `[ShockArc] 绘制:` 里 `弧=…/目标=…`
   （单人近距应接近 `88`）与 `顶点=…`（接近 6~7k）。**日志里永远不该出现** `本帧顶点数达到硬上限`。
2. **颜色两档**：画面里应同时看到两种弧 —— 一部分是"白芯 + 饱和**明蓝**外晕"（明蓝档），
   一部分是"近白偏蓝"（白蓝档）；中远距离上不再整体糊成白。
   客观口径：日志 `弧档实测=长…条(…) 明蓝…条(…)`，明蓝应稳定在 **40%** 左右。
3. **长度 1/3 长、2/3 短**：约每 3 条里有 1 条明显更长（0.45~0.95 格，且更粗一档），
   其余是贴身的小跳弧；两者随机混杂，不是按顺序排。
   客观口径：日志 `长度=短档 0.10~0.28格(67%) + 长档 0.45~0.95格(33%)` 与 `弧档实测=长…条(33%)`。
4. **不黑屏**：本 pass 与开关 1 共用同一条早就验证过的路径（没动 blend 节点 / 没动全局 blend /
   没抢采样器）。万一异常，`/yiz fxtoggle 4` 关掉即完全消失 ⇒ 可判定是不是这一层。
5. **不糊屏 / 不发灰**：
   - 近处一片白（糊）：把 `APPARENT_GAIN` 从 320 降到 256（=1.6×）或 192（=1.2×）即可，其它不用动；
   - 还是偏白/发灰：把 `BLUE_FRAC` 从 0.40 提到 0.50，或把 `HALO_WB_R/G` 调深（0.34/0.56 → 0.26/0.46）；
   - 明蓝太"电"了：把 `COLOR_BLUE_R_MIN/MAX`、`COLOR_BLUE_G_MIN/MAX` 整体上调（例如 0.35~0.50 / 0.62~0.75）。
