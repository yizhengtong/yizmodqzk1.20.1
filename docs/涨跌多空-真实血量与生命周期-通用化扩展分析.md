# 涨跌多空「真实血量 / 生命周期 / 掉落」通用化扩展分析（1.20.1）

> 目标：在不针对任何单个模组（无类名/字段名/包名硬编码）的前提下，把现有
> 「涨跌多空」攻击线的技术范围，从「改 Float 血量字段/通道 + 合成死亡链」扩展为
> 「任意血量存放形态 × 任意死亡/移除门控 × 模组原生链优先」的通用四层管道。
>
> 说明：本文引用三个模组（iss_csw / Mbt_mobs / scourge）的源码与反编译结果，
> **仅作为归纳防护/存放模式的样本**（与 `key-hunter-design.md` 同款方法论）：
> 归纳出的模式是通用的，方案与代码不含任何针对这三个模组的硬编码。

## 一、现状盘点：现有攻击线架构

现有链路集中在 `yizmodqzk`（1.20.1 移植版），入口为
`EntityASMUtil.applyProportionalDreamDamage`（涨跌多空等比累积软压 + 跨阈值触发）：

```
攻击命中（FIRST_DREAM 属性 > 0）
  │
  ├─ 0.  HealthMapRegistry.readHealth/tamperHealth   （静态 Map<实体,Number> 藏血）
  ├─ 0b. DynamicHealthAccessor.tamper                （两个 Float 通道差值为血量 + 独立死亡标记）
  ├─ 0c. DeathMarkerAccessor.tamperToDead            （Boolean DataParameter 强制判死标记）
  ├─ 1.  EntityHealthLocator.applyPersistentDamage   （Float/Double/Int/Long 字段 + Float 通道，
  │       行为验证定位、写后验证、回滚、JSON 缓存）
  ├─ 1b. DirectHealthFallback.forEachFloatItem       （反射直写所有 Float DataItem）
  │
  ├─ 等比累积：DREAM_ACCUM += dream/maxHp；delta 软压 = -maxHp×min(accum,1)
  │       （getHealth/isAlive/isDeadOrDying 被 agent 注入 special* 钳制为 min(值, maxHp+delta)）
  │
  ├─ accum ≥ 1  → dreamDeathblow：setHealth(-inf) + recordDamage + die()（MethodHandle 虚分派）
  │                 + 清 goals/brain + 未死补 dropAllDeathLoot + kill() 兜底 + 25 tick 后 forceRemoveDeep
  └─ accum ≥ 10 → dreamDeepRemove：forceRemoveDeep（世界存储三层反注册 + 移除包）
```

**配套基础设施**：
- `LivingHealthTransformer`（Java agent / ASM）：包装所有类的
  `getHealth/getMaxHealth/isAlive/isDeadOrDying`（方法自身返回值 + 全部调用点）→ delta 软压生效面；
- `LivingEntityMixin`：delta 通道定义、getHealth/isAlive/isDeadOrDying RETURN 截断、
  hurt()/setHealth() 伤害修正、die() 清理、NBT 持久化；
- `EntityRemovalUtil`：MethodHandle `Entity.remove` 基类直调 → Unsafe 置 removed →
  `forceRemoveDeep`（EntitySection / EntityLookup / entityTickList / chunkSource / 主动移除包）；
- `HealthModificationScheduler`：延迟/周期任务（死亡后强删等）。

### 现有技术的隐含假设（攻击面模型）

1. **真实血量必以"数值"形态存在**：Float/Double/Int/Long 字段，或 Float DataParameter；
   数值与 `getHealth()` 之间是**线性直映**（写 ±delta → 读 ±delta）。
2. **死亡 = 血量归零**：把数值打到 ≤0 或设独立判死标记，`isDeadOrDying()` 就会翻 true，
   vanilla 死亡链（`die → dropAllDeathLoot → remove`）随之生效。
3. **移除 = remove()/setRemoved()/世界存储反注册**，掉落 = `dropAllDeathLoot`。

下面三个样本恰好把这三个假设**同时打穿**，因此是绝佳的模式样本。

## 二、三个样本实体的逆向结论（仅作模式归纳）

### 2.1 无名术士 NamelessWizardsEntity（iss_csw）

来源：`[交错织法] iss_csw-0.3.0-fix`，`org.xszb.interlace_spellweaves.entity.boss.nameless_wizards.NamelessWizardsEntity`
（继承 `UnRemoveBossEntity` ← `BossEntity`）。

| 层面 | 实现 | 对现有链的意义 |
|---|---|---|
| 真实血量存放 | **String DataParameter** `DATA_EXISTENCE`，格式 `"HEC"+float`（混淆前缀串）；`getExistence()` 解析 `substring(3)`；`getExistenceNum() = maxhealth − existence` | 非 Float 通道 → `detectViaDataItems/DataAccessor` 跳过；`getHealth()` 返回常量（maxhealth 或 DEAD 相推导）→ 字段行为验证永不跟随 |
| getHealth/getMaxHealth | `getHealth()` 返回 `maxHealth`（除非 `ActType.DEAD`）；`getMaxHealth()` 返回静态配置 `NameLessWizardConfig.maxhealth` | 字节码探测读不到 float 字段；delta 软压只能钳"显示"，钳不到存在值 |
| 死亡门控 | `getCanDie() = NOTDIE(Boolean DataParameter) && !antiCheat`；`die()` 自定义：`!isRemoved && !dead && !antiCheat` 才执行 `dropAllDeathLoot + IllusionExplode + PocketDimSavedData.resetDeathCount` | 需"解除门 + 走原生状态机"两条路，不能只调 die() |
| 反作弊门 | `setAntiCheatMode(true)` → existence=0、canKill=false、canDie=false、传送回家、幻影爆炸；`remove()` 被门控时**自动进入反作弊** | 探测/直写若被感知会直接触发惩罚态 |
| 相位状态机 | `ActType`（NONE→BREAK2→PHASE→DEAD…）由 tick 驱动；phase2 且 `existenceNum ≤ 0` 才进入 DEAD | 原生死亡链 = 让 existence 越过阈值，**由模组自己过渡**，而非强调 die() |
| 模组自带通用工具 | `EntityUtil.setHealth`（分层：vanilla 通道 → ASMHealthMethodHelper → setHealthAccessors（Float **+INT** 通道）→ MethodHandle → LifeValueContainerScanner 可达对象图+Map 直改）、`EntityUtil.forceRemoveEntity`、`noInvincibilityFramesHurt` | 证明"模组自研通用链"是普遍存在的**可发现模式类** |

### 2.2 基岩傀儡 BedrockGuardian（Mbt_mobs）

来源：`Mbt_mobs-1.2.0.0.1_publish_ver`，`Mobiaton.mobiaton_01.entity.Guardians.BedrockGuardian`
（继承 `GuardianHealthBase`）。

| 层面 | 实现 | 对现有链的意义 |
|---|---|---|
| 真实血量存放 | 实例 **float 字段 `encAcc`/`encLastAcc` = scramble(累加伤害)**，`scramble(v) = Float.floatToRawIntBits(v) ^ SCRAMBLE_KEY`（实例 final int，Bedrock 为 1513910768）；`getHealth() = BOSSMX(1000) − descramble(encAcc)`，**双读一致性校验**（读两次 encAcc，中途变化则取首读） | 直写 ±delta 后 `getHealth` **非线性跟随** → 行为验证失败；双读校验让"写-读-还原"探针容易被察觉 |
| setHealth/heal | **空实现（no-op）**；`getAttribute(MAX_HEALTH)` 被换成 KNOCKBACK_RESISTANCE 实例 | 常规改血面全部失效 |
| 伤害门控 | 只在 `actuallyHurt` 累加：singleHitCap=1.0、progressiveCap=1.0、hpUpdateRate=5tick、regen 1.0/40tick；tick 每 5 秒同步一次"显示血"到 vanilla 通道 | vanilla 通道是**显示通道**，每 tick 被 `syncDisplayHealth` 覆盖；真实数值只在 encAcc |
| 死亡/移除门控 | `mobiaton_debug`（首服 tick 后置 false）：`setRemoved/remove/die` 在 !debug 时**全部拦截**（只 markExternalAttack 重同步）；`setLevelCallback` 包装 onRemove（写 null + revive）；`tick` 检测 `isRemoved` → `revive()`；`shouldBeSaved=false` | remove()/die() 全空转；合成链强删后**下一 tick 复活** |
| 模组原生移除入口 | `mobiatonDebugger(String)`：key=="mobiaton" → debug=true → `setRemoved(KILLED)`（此时超类 remove 放行）；tick 内 `readDmgAccPlain() >= BOSSMX−1` 时调用并 discard | **原生链 = 把 encAcc 打到 BOSSMX−1 以上，让模组自己"验尸放行"** |
| 模组自带通用工具 | `AttackMethods`：`mobiatonDebugger(entity)`（沿继承链找该方法并调）、`systematicSetHealth`（setHealth→specialSetHealth→deepSearchHealthOnly→Tier2 管理器劫持）、`killEntity`、`ultimateErase/eraseEntityFromWorld/systematicDiscard/eliminate`；`HealthHandler.healthHandler` 单例（track/setHealth/markForceDie/markForceRemove）+ `HealthHijackPlugin` coremod 向**所有 Entity 子类**注入 getHealth/setHealth/isDeadOrDying/isRemoved 的门控读取 | 又一个"模组自研 kill/remove 链"，且是**注入到所有实体**的通用机制 |

### 2.3 路西法 LuciferEntity（scourge）

来源：`[天灾] scourge-1.1.1-forge-1.20.1`，`net.mcreator.scourge.entity.LuciferEntity`（MCreator 生成，SRG 名）。

| 层面 | 实现 | 对现有链的意义 |
|---|---|---|
| 真实血量存放 | **Integer DataParameter `DATA_ERealHealth`**（初始 1000）；`getHealth()` 直接返回它 | 非 Float 通道 → 现有 Float-only 探测/直改全跳过；INT 通道 `entityData.set` 可直写但现有链不认 |
| setHealth 门控 | `setHealth(h)` 仅当 `h ≥ 内部值` 才生效（**只允许加血**） | 走 setHealth 的伤害面全灭；只能绕过 setHealth 直写通道 |
| hurt 门控 | 免疫大量 DamageType + `LuciferHurt3Procedure` 判定 | 走 hurt 的伤害面受限 |
| 移除门控 | `remove(RemovalReason)` **空实现**；tick 每帧 `dead=false, deathTime=0`，且 `isRemoved() → revive()` | 合成链强删后**每帧复活**；必须"永久死亡抑制" |
| 原生死亡/掉落链 | 全在 `LuciferETProcedure`（每 tick，PersistentData 标签 `ESkill/ESkillCooldown/EDeath`）：flamei 分支 → `EDeath=2` → `DATA_ERealHealth = ceil(maxHealth×0.1)`；半血进二阶段；1503 行附近以 **ItemEntity 直生**掉落 `HALO_OF_SINS`；`LuciferCheckProcedure` 维护全局 `ScourgeModVariables`（lucifer_live/pos/health/repeat…） | 掉落与"死亡"由模组状态机 + 全局变量驱动，vanilla `dropAllDeathLoot` 根本不参与 |

## 三、失效环节逐项映射（为什么现有链打不动）

| 现有环节 | 无名术士 | 基岩傀儡 | 路西法 |
|---|---|---|---|
| ① `EntityHealthLocator`（字段/通道 + 行为验证） | DATA_EXISTENCE 是 **String 通道** → 跳过；getHealth 常量 → 永不跟随 | encAcc 是 **XOR 编码字段** → ±delta 直写不线性跟随；双读校验干扰探针 | DATA_ERealHealth 是 **INT 通道** → Float-only 跳过；无普通字段 |
| ② `DirectHealthFallback`（全 Float DataItem） | String 通道不动；vanilla 通道只是显示 | vanilla 通道每 tick 被 `syncDisplayHealth` 覆盖；encAcc 不在 DataItem | ERealHealth 是 INT → 不动；vanilla 通道是显示 |
| ③ `DynamicHealthAccessor`（差值 Float 通道） | 无 Float 差值 | 无 | 无 |
| ④ `HealthMapRegistry`（静态 Map） | 无 | 无 | 无 |
| ⑤ `DeathMarkerAccessor`（Boolean 判死标记） | NOTDIE/CANKILL/YOU_CHEAT 是**门控**不是标记（设 true 不翻 isAlive） | isAlive 读 encAcc，无通道 | 无 |
| ⑥ delta 软压 + agent special* 钳制 | 只钳显示；isDeadOrDying/die/remove 走存在值与门控 | isDeadOrDying 覆盖读 encAcc；tick 死亡检查直读 encAcc | 只钳显示；ETProcedure 直读 ERealHealth |
| ⑦ `dreamDeathblow`（die+drop+kill+deepRemove） | die() 有反作弊门，可能空转/假死复活；模组状态机（ActType/PocketDimSavedData）不同步 | die() 空实现 → 只补 vanilla 掉落；kill 无效；forceRemoveDeep 强删后 tick **revive 复活**；模组自移除（mobiatonDebugger）与模组掉落链没跑 | die() 走 vanilla → 只出 vanilla 掉落；remove() 空 + tick revive → 实体残留；EDeath/全局状态没跑 → 模组掉落（HALO_OF_SINS）与全局重置缺失 |

**一句话归纳**：现有链是「**找数值槽 → 打数值 → 走 vanilla 死亡**」的单型管道；
三个样本分别展示了「非数值形态存储（String/INT/编码）」「门控式生命周期（canDie/反作弊/remove 空实现/复活）」
「模组自管死亡-掉落状态机」三类**系统性质的不兼容**，不是补一个字段就能解决的。

## 五、通用化扩展架构（深度：四层管道 + 两个横切设施）

核心思路：把「找字段直写 + 打数值 + vanilla 死亡」升级为
**存储解析 → 门控判定 → 状态机适配 → 触发编排**的四层管道，
任何一层都遵循「**类型特征 + 行为验证 + 可配置**」三原则（不写死任何模组名）。

### 5.1 层一：存储解析层（HealthStorage SPI）

把现有各检测器收敛为统一的 `HealthStorage` 接口：

```java
public interface HealthStorage {
    // 返回该存储类型的规范化槽描述（不依赖字段名）
    Slot detect(LivingEntity e);
    double read(LivingEntity e, Slot s);
    boolean write(LivingEntity e, Slot s, double value);   // 返回是否真实生效
    boolean verify(LivingEntity e, Slot s, double before); // 写后验证（可选）
    void rollback(LivingEntity e, Slot s, double before);
}
```

新增的 Provider（全部行为验证驱动，无名字假设）：

- `NumericAccessorProvider`：把现有 Float-only 扩展为 **Int/Long/Double/Short/Byte** DataParameter。
  行为验证：直写 `cur±1` → `getHealth()` 跟随方向；对 INT 通道（Lucifer 型）直接用
  `entityData.set` + `onSyncedDataUpdated`（绕 setHealth 门）。
- `StringCodecProvider`：对 **String DataParameter**，探测「前缀 + 数值」形态（解析尾部/前缀可解析数值），
  写-读往返验证 `getHealth` 跟随（NamelessWizard `"HEC"+f` 型；本家 SECURE_OBF 已有 key，可复用同一解码描述符）。
- `EncodedFieldProvider` + `BlackBoxInverseSolver`：对**编码字段**（XOR/缩放/偏移/取反），
  **不猜编码**，用黑箱反函数逼近：写一组探针值 `w`，记录 `getHealth` 响应 `h(w)`，对目标血量做
  二分/查表求解 `w*` 使 `h(w*) = 目标`（BedrockGuardian 的 XOR 自反变换天然可解；缩放/偏移同理）。
  - 探针纪律：单 tick 内完成、双读一致性实体（BedrockGuardian）用「写入 → 立即读 → 还原」且
    期间不 yield；探针值先备份 `encLastAcc` 同步写，避免触发 `applyProgressiveCap` 拉回。
- `AccumulatorProvider`：识别「累加器 + lastAcc + 进度钳」形态（S7）：方向 = 写 +v → getHealth −v（inverse），
  并**读出钳制参数**（singleHit/progressive/rate），把"一次扣血"换算为"累加器等价增量 × 解除钳制的直写"。
- `SingletonManagerProvider`（P2，可配置）：识别「UUID → 血量」单例管理器（S9）：类型特征 =
  静态单例字段 + 泛型 Map<UUID,Float> + `contains/setHealth/getHealth/shouldDie/shouldRemove` 方法形状；
  **经配置文件声明模板**（模式模板而非类名），由行为验证确认后复用其原生链。

### 5.2 层二：门控判定层（LifecycleGate）

把 `DeathMarkerAccessor` 泛化为 `LifecycleGateAccessor`，行为探测四类门：

- **死亡门（canDie）**：Boolean 通道值 false ↔ `isDeadOrDying()` 恒 false 或 `die()` 空转；
  探测：翻 false → `isDeadOrDying` 不随血量变化；翻 true → 恢复。
- **击杀门（canKill）**：Boolean 通道 ↔ `remove()`/`die()` 被拦。
- **反作弊门（antiCheat）**：Boolean 通道 ↔ 触发后 isAlive/remove 行为变化（NamelessWizard 型）。
  **关键：探测本身不得触发惩罚** —— 对 G8 型每 tick 校验实体，探针前先"冻结感知"（见 5.5）。
- **移除门（removeBlocked/revive）**：调 `remove()` 后 `isRemoved()` 仍 false，或下一 tick `revive()`；
  探测一次即缓存 `REVIVES` 集合。

输出 `GateSlot { kind, accessor/field, activeLevel }`，供层四决定「解除门走原生链」还是「绕过门走合成链」。

### 5.3 层三：状态机适配层（StateMachineAdapter）

针对「死亡/掉落由模组自管状态机驱动」的实体（G4/D3），提供**原生状态播种**：

- 识别实体的"死亡触发存储"（层一已定位的槽，如 NamelessWizard 的 existence、Lucifer 的 ERealHealth、
  BedrockGuardian 的 encAcc），**把数值播种到模组自己判死的阈值**（existence→maxhealth、ERealHealth→0、
  encAcc→BOSSMX−1），然后**让模组自己的 tick 状态机过渡**（1~3 tick 观察窗口）。
- 观察期后校验：模组是否自行进入死亡/掉落/移除（`isDeadOrDying`、`dead` 标志、掉落实体、全局变量）。
  - 已进入 → 原生链成功，**零合成干预**（掉落、阶段特效、全局状态全部由模组完成，最干净）；
  - 未进入 → 降级合成链（层四）。
- 状态机**入口发现**（P2）：行为式发现「翻门自移除」方法（BedrockGuardian `mobiatonDebugger(String)` 型：
  方法使 `isRemoved()` 从 false→true 且之后 remove() 放行），用探针验证 + 配置模板固化，不硬编码名字。

### 5.4 层四：触发编排层（KillChainOrchestrator）

```
原生链优先（保留模组全部语义）：
  1) 存储解析 → 把数值播种到模组判死阈值（层三）
  2) 解除死亡/击杀/反作弊门（层二，若可解除）
  3) 等待状态机过渡（≤3 tick），校验掉落/移除是否由模组完成
  4) 未完成 → 调用"翻门自移除"原生入口（层三发现，若存在）
合成链兜底（保证语义完整）：
  5) 零血播种（所有已解析槽 + vanilla 通道 + recordDamage + lastHurtByPlayer）
  6) die()（虚分派到 override，模组门已解除时其内掉落自动跑）
  7) 掉落补齐：模组掉落未出现 → 按 loot table 调 dropAllDeathLoot + 经验/归属；
     仍无 loot table → 记录"模组掉落缺失"并保留合成记录供配置挂钩
  8) 永久死亡抑制：dead=true + removalReason 非空 + levelCallback=NULL + forceRemoveDeep
     + 调度器 2~3 tick 复扫（对 tick-revive 实体，扫到即再反注册，直至消失）
  9) 全局状态清理钩子（可配置：重置模组全局变量的方法签名模板）
```

### 5.5 两个横切设施

- **编码/解码注册表 `CodecRegistry`**：集中管理「存储值 ↔ 逻辑血量」的变换描述符
  （plain / inverse / xor / scale+offset / prefix-string / key-obf），
  由行为探针**推断**描述符类型（写探针值、读响应方向与线性度），新模组无需改码。
- **感知抑制 `ProbeDiscipline`**：行为探测的安全纪律（防 G8 反作弊误触发）：
  - 探测窗口内禁止跨 tick（写-读-还原同一 tick 完成）；
  - 双读一致性命中时改用"整槽替换"探针（备份 encAcc+encLastAcc 同写同还原）；
  - 对已识别反作弊门的实体，探测前先记录门状态，探针失败立即还原并**放弃该类**（进 NEGATIVE 缓存）；
  - 探测结果全量进 `entity_health_slots.json` 的**升级版** `health_patterns.json`（含门/状态机/复活信息），
    重启后可跳过重复探测。

## 七、风险与边界

1. **行为探测有副作用**：写-读-还原探针可能被 G8 型每 tick 校验感知（BedrockGuardian 双读、
   NamelessWizard tick 校验）→ 必须遵守 ProbeDiscipline；误触发反作弊 = 该实体永久惩罚态。
2. **MCreator/生成代码可再生成**：scourge 类名/方法名随版本漂移 → 一切依赖行为特征，不依赖名字；
   SRG 名（`m_21223_` 等）已双名匹配，需保持。
3. **强删与复活竞态**：Lucifer/BedrockGuardian 的 tick-revive 与合成链强删存在时序竞态 →
   复扫任务必须持续到实体确实消失；强删时先置 `levelCallback=NULL` 再反注册，杜绝 onRemove 复活路径。
4. **原生播种的"观察窗口"成本**：状态机过渡需 1~3 tick，涨跌多空高频攻击下要合并/去重播种，
   避免同一实体每 tick 重复播种。
5. **掉落语义**：合成链只能补 vanilla loot table；模组专属掉落（ItemEntity 直生 + 全局变量）
   只能靠原生链或配置钩子，无法 100% 通用推断 —— 这是诚实的能力边界。
6. **性能**：黑箱反函数求解（每目标 5~10 次探针）与全类普查需缓存 + 节流（复用
   `HealthMapRegistry` 的类增长重扫机制）。

## 八、结论

- 现有「涨跌多空」链是**单型数值管道**，对 S3/S4/S6（非 Float/编码存储）、G2/G3/G4/G7
  （门控与复活）、D3（模组状态机掉落）三类系统性质不兼容，三个样本恰好各踩一类。
- 通用化方向不是"为每个模组加一个字段名"，而是把攻击面从
  「存储值 → vanilla 死亡」升级为「**存储解析 → 门控判定 → 状态机适配 → 触发编排**」四层管道，
  全部以类型特征 + 行为验证 + 配置模板驱动（延续 key-hunter-design 的方法论）。
- P0（非 Float 数值通道 + String 串 + 编码黑箱求解 + 累加器）**纯增量、无针对**，
  即可让三个样本的"真实血量"部分全部打通；P1 打通门控与复活；P2 通过配置模板
  复用模组自研原生链，补齐掉落与全局状态语义。
